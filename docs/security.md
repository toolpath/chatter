# Security

## Report a security problem

Do not open a public issue for a security problem. Other people can read it before a fix is ready.
Open the **Security** tab of the repo, click **Report a vulnerability**, and fill in the form. Tell us:
- What the problem is, and what an attacker can do with it
- The steps to make it happen
- The Chatter version
- How you run Chatter (the Pi card or Docker, and the operating system)

We fix security problems only in the newest version. To get a fix, [update Chatter](./guide/update.md).

## How Chatter is made to be used

Chatter is made for a **shop network that you trust**, behind a firewall. Do not make it open to the internet.

These limits are known. They are not bugs, but you must know them:

- **Every computer on the network can open Chatter** on port 3001. On Linux, a ufw or firewalld rule does not stop them, because Docker sends the traffic of a published port around these rules. To let only some computers reach Chatter, see [Limit who can reach Chatter](#limit-who-can-reach-chatter).
- **Docker can also publish port 3001 on the IPv6 addresses of the computer.** Then other computers can open Chatter on an IPv6 address, also when a rule for IPv4 stops them. To see the addresses, run `docker port chatterbox`. A line with `[::]` is for IPv6. To stop this, publish the port on one IPv4 address (see [Limit who can reach Chatter](#limit-who-can-reach-chatter)).
- **No HTTPS by itself.** Other people on the network can read the login cookie, and the password that a program sends. To use HTTPS, put a reverse proxy in front of Chatter (see [Use HTTPS](./guide/https.md)). A login cookie from plain HTTP gets the Secure flag when the browser uses it over HTTPS. This does not stop a copy that a person read before. After a move to HTTPS, each user clicks **Log out**, logs in again through the proxy, and then clicks **Log out all other browsers** (see step 5 in [Use HTTPS](./guide/https.md)).
- **Chatter sends no HSTS header.** HSTS tells a browser to use only HTTPS for an address. On a LAN address with plain HTTP, it can lock the users out. If your proxy gives HTTPS, the proxy can send HSTS. Chatter sends the other security headers: other sites cannot show Chatter in a frame, and the page loads scripts only from Chatter.
- **Chatter accepts at most 256 connections at a time.** This keeps file handles free for the database, the log and the machines. Chatter closes a connection that does not send its request headers in about 20 seconds. Each login can have 5 live update streams. When a login opens a 6th, its oldest stream closes. A computer on the network can still use all 256 connections, and then other browsers cannot open Chatter until it stops.
- **Wrong passwords cause a wait.** After 10 wrong passwords for one user from one computer in 15 minutes, that computer must wait before it can try that user again. The other users of that computer can still log in. After 30 wrong passwords for one user from all computers in 15 minutes, nobody can log in as that user. Each wait ends 15 minutes after the first wrong password, so it can be shorter than 15 minutes. Good logins do not count. A good login does not end the wait for a different user. Chatter counts all IPv6 addresses in one /64 network as one computer. Browsers that are logged in, and programs whose login worked before, keep working during a wait. An Admin can end a wait in **Settings > Logins**. A restart of Chatter also ends each wait.
- **The server log has each password try.** Chatter writes an info line for each good login and each password change. Chatter writes a warning for each wrong password, each unknown username and the first try of a computer that must wait. Each line has the username, the address of the computer and the result. The result is `logged-in`, `password-changed`, `wrong-password`, `no-such-user` or `locked`. The line never has the password or the login cookie. Chatter writes only the first 20 tries with an unknown username from one computer in 15 minutes. Then it writes one warning that it does not write the next tries from that computer. So a computer that sends many random usernames cannot push the older lines out of the log. The login log on **Settings > Logins** still has these tries. A program that uses HTTP Basic gets a line only for its first login, not for each request. Chatter also writes a warning when the first-run setup makes the Admin, with the address. For the warning of `npm run reset-password`, see [Forgot a password](#forgot-a-password). If a person types a password in the username field, the password shows in the log as the username.
- **Anyone on the network can lock a user on new browsers.** A person who knows a username, for example `admin`, can send 30 wrong passwords from 3 or more computers. Then nobody can log in as that user from a new browser for up to 15 minutes. The person can do this again after each lock. A known browser (see the next item) can still log in. Chatter writes a warning in the server log when a user lock starts, with the username and the address of the last try. To get in again, see [Locked out after wrong passwords](#locked-out-after-wrong-passwords).
- **A browser where you logged in before is a known browser.** After a good login, Chatter gives the browser a device cookie for 400 days. This is longer than a login (1 year at most), so the browser is still known when its login ends. Each good login gives a new cookie. Chatter signs the cookie with a key in the data folder (`device-key`, next to `chatter.db`). The cookie holds no password. The lock of a user and the wait of a computer do not stop a known browser. A known browser has its own limit: after 10 wrong passwords in 15 minutes, that browser must wait. A browser is known only for the last user that logged in on it. These actions stop the device cookies of a user:
  - A new password, from the user or from an Admin. The browser where you changed your password gets a new cookie.
  - **Log out all other browsers** in **Settings > Your account**. This stops the device cookies of each other browser of that user, also of a browser that is logged out. The browser where you clicked the button gets a new cookie, so it stays a known browser. The device cookies of other users stay.
  - The removal of the user by an Admin.
  - `npm run reset-password`. This stops the device cookies of each user.

  An Admin unlock does not stop a device cookie. Programs that use HTTP Basic have no device cookie, so they always have the normal limits. The server log line of a password try from a known browser has `knownDevice=true`.
- **A shared computer stays known after log out.** Log out does not remove the device cookie. So the next person at that browser gets the limit of a known browser for the last user: 10 password tries in 15 minutes, also while that user is locked. To stop this, use **Log out all other browsers** from a different browser, or change your password. On a shared computer, use a private browser window, or remove the cookies of Chatter after you log out.
- **Some setups show one address for all computers.** On Docker Desktop (Mac and Windows), and for IPv6 through the Docker port, Chatter sees the same address for each computer. Then the wait of one computer applies to each person in the shop, for that user. Do not trust the Docker network gateway as a proxy to fix this, because each computer can then send a false address.
- **Trust only the address of your proxy** in **Settings > HTTPS and proxy**, or with `TRUST_PROXY`. A wrong address lets a computer hide its real address, and so get around the wait after wrong passwords.
- **FTP is not encrypted.** The FTP username, the FTP password, and the files go over the network as plain text.
- **One FTP connection to each machine.** Many CNC FTP servers accept only one connection. A second connection can fail, or put the control in a bad state. So Chatter does the FTP tasks of one machine one after the other, and opens at most one FTP connection to each machine at a time. A task waits at most 3 minutes for its turn, and at most 5 tasks wait for one machine. Then Chatter refuses the task with the error "The machine is busy with other file tasks" (HTTP 503). A long task can keep the other tasks of that machine waiting. A download stops after 30 minutes, and an upload stops after 30 minutes. These limits start when the task gets its turn. When a user cancels a task, or closes the browser, Chatter stops the task, also while it waits, and the next task starts. An upload is different: the browser stops an upload only while it waits. When the upload runs, Chatter completes it, so the machine does not keep part of a program. Only the 30-minute limit or an error of the machine stops a running upload. The log then gets a warning that the browser left during the upload. Chatter does not control other programs on your network. A DNC program, or a second Chatter, can still open a connection to the same machine. If you add the same address as two machines in Chatter, each machine has its own queue. Then Chatter can open two connections to that address.
- **Each role can make the file tasks of a machine wait.** A Viewer can ask for the file list of a machine. A file list can take up to 2 minutes, and other file tasks wait for it. Requests for the same list share one file list. At most 2 file lists of different folders wait for one machine. Then Chatter refuses the next one at once with "The machine is busy with other file tasks". So file lists cannot fill the queue of a machine, and a send or a download of an Operator can still wait for its turn. But a person or a program with a Viewer login can ask for file lists again and again. Then the sends and downloads of that machine wait, and can fail after 3 minutes.
- **Chatter holds the files of an upload in memory.** Chatter reads the files of an upload (at most 32 MB) into memory before it sends them to the machine. This can use about two times the size of the files. So Chatter does at most 2 uploads at the same time, for all machines, and at most 1 upload to each machine. When 2 uploads run, Chatter refuses the next upload at once with "Chatter is busy with other uploads" (HTTP 503), before it reads the files. When an upload to a machine runs, Chatter refuses the next upload to that machine at once with "The machine is busy with other file tasks" (HTTP 503). An upload that waits for a busy machine keeps its place. So uploads to 2 busy or slow machines can stop the uploads to all other machines for up to 33 minutes: at most 3 minutes of wait for the turn, and then at most 30 minutes for the upload. Only an Operator or an Admin can send files.
- **A machine can send a very long file list.** Chatter has limits, so a bad or broken FTP server cannot fill the memory of a Pi or keep Chatter busy. Chatter reads at most 1 MB of one folder list. One file list has at most 5000 files and folders and at most 5 folder levels. For one file list, Chatter opens at most 200 folders and stops after 2 minutes. Then the **Files** tab of the machine tells that the list is cut short. After a folder list that is too long, Chatter opens no more folders. When the folder list is too long or too slow before an upload, the upload stops, because Chatter cannot know if the file is there.
- **A machine can send a reply with no end.** A broken control, or a different device at the address of a machine, can send data and never stop. For Brother, Haas and MTConnect, Chatter has a limit for each reply, so the memory of a Pi does not fill. The limit is 1 MB for a Brother reply and for a line of the Haas data stream. It is 64 KB for a reply on the Haas query port. For an MTConnect agent, it is 4 MB for the `/probe` reply and 1 MB for the `/current` reply. These limits are much larger than the replies of real machines. When a reply is larger than its limit, Chatter stops the reply and closes the connection. Then the machine shows the error, and the log gets a warning with the machine and the limit. At the next poll, Chatter connects again. For a Siemens control, Chatter sets no limit of its own. The OPC UA library takes its message limits from the control.
- **A machine can send a very large or very slow file.** Chatter downloads at most 64 MB of one file, and stops a download after 30 minutes. When the browser reads slowly, Chatter reads slowly from the machine, so the file does not wait in the memory of the Pi. When the browser stops a download, Chatter stops the transfer from the machine too.
- **Some old machines do not confirm the end of a download.** After a file, an FTP server must send a reply (usually `226`). Some old machines never send it. So before each download, Chatter asks the machine for the size of the file (`SIZE`), and waits at most 3 seconds for the answer. When the machine closes the data connection correctly, and no reply comes in 3 seconds, Chatter compares the bytes with that size. If Chatter has fewer bytes than the size, the download gives an error. If Chatter has more bytes than the size, Chatter accepts the file, and the log gets a warning. Some controls change a program while they send it, so the file can be larger than the size. If the machine gives no size, Chatter accepts the file, and the log gets a warning with the machine, the file and the number of bytes. If the machine does not answer `SIZE` in 3 seconds, or closes the connection, Chatter connects again and downloads the file with no size. A broken or bad FTP server that gives no size, or a size that is too small, can thus cut a file short with no error. A data connection that breaks, or that stops in the middle, always gives an error. An error reply (for example `426`) always gives an error.
- **A folder list can end before it is complete.** Chatter waits for the reply of the machine after each folder list. When the machine sends an error reply (for example `426`) after part of the list, or breaks the data connection, the **Files** tab tells that the list is cut short. Chatter then shows only the complete lines of the list. Some old machines send no reply after a folder list. Some also keep the data connection open. When no reply comes, Chatter accepts the full list 1 second after the data connection closes correctly, or 1 second after the last data. New data starts this wait again. Some old machines answer `150` for an empty folder, and then send no data and no reply. A slow control can send its first data some seconds after the `150`. So after the `150`, Chatter waits at most 5 seconds for the first data. When no data and no reply come in these 5 seconds, Chatter accepts an empty folder, and the log gets a warning with the machine and the folder. If a folder shows as empty and the log has this warning, open the folder again. A broken or bad FTP server can thus cut a folder list short with no error. Chatter then closes the connection, so a late reply cannot go to the next command. For the next folder, Chatter logs in again. On a machine that sends no reply, each folder thus costs one more login. The file list then takes more time, and the 2-minute limit can cut a large file list short. When a new login fails, Chatter stops, and the **Files** tab shows the part of the list that Chatter read. When the machine sends its reply but does not close the data connection, Chatter accepts the list when no data comes in 1 second.
- **An upload that ends with an error can leave part of a file on the machine.** When the machine sends an error reply (for example `426`) after an upload, Chatter shows the upload as failed. But the machine can keep the part of the file that it got. With **Replace files with the same name**, that part can replace the old program. Send the file again, or delete it.
- **The machines have no login on their data ports** (Brother, Haas, MTConnect, FANUC). Anyone on the network can read the machine data from those ports. A Siemens control has a login only if you set one up for OPC UA (see [Siemens machines](./guide/siemens.md)).
- **A saved password goes only to the address where you saved it.** Chatter sends the FTP password, and the OPC UA password of a Siemens control, to the device that answers at the address of the machine. Chatter does not check that this device is your machine. When you change the IP address of a machine, or the port of a saved password (the FTP port, or the OPC UA port), Chatter does not send the saved password to the new address. You must type the password again, or click **Remove password**. The text under the password box tells you this before you save. If you do not, Chatter saves nothing and shows "Type the FTP password again" (or the OPC UA password). A new username does not move the password, because the password still goes to the same machine and port. So check the address before you type the password. A notification channel works in the same way: when you change its address (the web address of a webhook, the ntfy server, or the Apprise address), Chatter does not send the saved secret to the new address. You must type the secret again, or select **Delete the saved secret**. The Twilio, Telegram, and Discord channels have no address field in the form: their secret goes only to the service. For development only, `TWILIO_API_URL` sends the Twilio auth token to a different address (see [Develop](develop/index.md)).
- **Chatter accepts a new certificate of a Siemens control with no check by a person.** It does not check that the certificate is the same as before. So a device that answers at the address of the control can get the OPC UA username and password.
- **A login ends after 14 days with no use, and after 1 year at the latest.** Each request from the browser is a use. A visible Chatter page also counts as a use: it tells Chatter every 5 minutes that it is in use. So a dashboard on a screen stays logged in. A hidden tab, a tab behind other tabs or a minimized window does not count as a use. So a forgotten tab on a shared computer ends after 14 days. When a login ends, its live connection also ends within 30 seconds, and the page asks you to log in again. The login ends 1 year after the login, also when the browser is used each day. Log out stops the login of that browser, also a copy of its cookie. To stop your other logins, use **Log out all other browsers** in **Settings > Your account**, or change your password. To log out a different user, an Admin sets a new password for that user.
- **Give each person their own account, with the smallest role that they need.** A Viewer can see the machines and their history, and change their own password. A Viewer sees the names of the program files, but cannot download or read a program. A Viewer cannot start a read of the tool table (**Sync**). An Operator can also read, send, and delete files, and click **Sync**. An Admin can do everything.
- **The first visit sets up the first Admin.** Until an Admin exists, the first person who opens Chatter can make the Admin account. A web page from the internet that a person opens on a computer in the shop network can also use this step (with DNS rebinding). So set up Chatter at once after you install. After the first Admin exists, the setup stays closed. `npm run reset-password` does not open it again, because the command makes the new Admin itself (see [Forgot a password](#forgot-a-password)). When Chatter refuses a setup, the reply is always the same. So the reply does not tell if a username exists.
- **Anyone on the network can see the Chatter version** at `/api/health`, with no login. The update helper needs it. It also gives a random name of the server process, which changes at each start. The network scan uses it to tell this Chatter from another one.
- **Chatter asks GitHub once a day for the newest version.** It sends no machine data. To stop this, turn off **Check for updates on GitHub** in **Settings > Updates**.
- **Chatter runs the FANUC FOCAS2 library as program code.** The library can read each secret that Chatter keeps, such as the passwords and the tokens in `chatter.db`. Chatter keeps the file in the data folder. So the file stays after an update. A backup and a restore of the data folder include the file. In **Settings > FANUC library**, upload only the files that you got from FANUC. Then compare the SHA-256 fingerprint on that page with the fingerprint of your file from FANUC (for example, `sha256sum <file>` on Linux).
- **SSH on the Pi card is off, until you turn it on** in the Customisation of Raspberry Pi Imager. The user that you make there can use `sudo` with no password. So an SSH login gives full control of the Pi, of Chatter, and of `chatter.db`. If you turn on SSH, select a public key only, or use a strong password. On a card of Chatter 1.8.0 or later, **Settings > Diagnostics** shows if SSH is on. An update does not add this line, because the update helper stays the same. To turn it off, run `sudo systemctl disable --now ssh` on the Pi.
- **Notifications send alert text out of the shop network.** A message has the machine name, the alert, and the value, and can have the Chatter address. It goes to Twilio, to the web address of a webhook channel, to Discord, to Telegram, to an ntfy server, or to your Apprise server, which sends it on to your services. Only an Admin can add a channel. See [Notifications](./guide/notifications.md).

## Updates on the Pi card

Chatter itself cannot install an update. It only puts the update file and a request in a folder. A helper on the Pi, outside Docker, does the install.

- The helper installs only a file that is signed with the Chatter release key, and only a newer version. So a bad download or a bad upload cannot install.
- GitHub signs the update file in a separate job. Only that job gets the release key, and it runs no GitHub Action except the checkout. Each workflow pins its actions by a full commit.
- The sign job refuses a tag that is not on `main`. This check stops a mistake, but not an attack. For a tag, GitHub runs the workflow file of the tagged commit. So a person who can push to the repo can push a tag on another commit, with a changed workflow that skips the check and reads the key. The `release` environment gives the key to each tag such as `v1.2.0`. A tag ruleset and required reviewers on the `release` environment stop this attack. These settings are a separate item, and they are not on yet.
- Until these settings are on, a new tag on an old commit of `main` also gets a signed update file.
- The helper does not trust anything that Chatter says or puts in the folder. So an attacker who breaks into Chatter cannot use the helper to take control of the Pi.
- A newer helper also accepts the request `reboot`, and restarts the Pi at most once in 15 minutes. So an attacker who breaks into Chatter can restart the Pi, but cannot keep it down.
- A newer helper writes `network.json` (the addresses of the Pi, the gateway, and if SSH is on) and `helper.log` for **Settings > Diagnostics**. It writes each value only when the value has the expected shape.

## Diagnostics

Only an Admin can use **Settings > Diagnostics** and the routes behind it: `/api/logs`, `/api/logs/stream`, `/api/logs/debug`, `/api/support-bundle`, `/api/system/facts`, `/api/system/restart-chatter`, `/api/system/restart-pi`, and `/api/updates/helper-log` (the role must manage updates).
Only an Admin can test or reconnect a machine: `/api/machine/:id/test` and `/api/machine/:id/reconnect` (the role must manage machines).
Each logged-in user can read the connection of a machine: `/api/machine/:id/health`.

- **The log hides secrets.** Before Chatter writes a line, it hides each value with a name such as password, token, secret, authorization, API key, or cookie, the user and password in an address, secret values in the query of an address, and the tokens in Telegram, Discord and Slack addresses. The log in memory, the log file, the log download, the live log, and the support bundle get only the hidden lines.
- **The support bundle hides the saved secrets, but not all text.** The machine settings lose each password field: they tell only if a password is saved. The notification channels have their type, name, and routing only: not their saved settings. The messages have their status and error, not their text. But an error text or a log line can contain an address, a topic, or a phone number. The support bundle is for your own support. Read it before you send it to another person.
- **The connection test uses only the saved address and ports of the machine.** The request has no address, so nobody can use it to reach another computer. Chatter allows one test of a machine at a time, and one in each 10 seconds. The texts are fixed: no text from the machine is shown. The test does not use ping.
- **The restarts are logged with the user name.** Restart Chatter ends the process, and Docker starts it again. Restart the Pi only writes the request `reboot` into the update inbox. The helper checks it as strictly as an update request (see below), restarts the Pi only when it does not check or install, and at most once in 15 minutes.
- **The live log has limits**, so a forgotten browser tab cannot fill the memory of the Pi: at most 3 live logs, and 200 waiting lines for each. A slow browser loses lines, and Chatter tells how many.
- **The log file** is in the data volume, next to `chatter.db` (`logs/chatter.log`, at most 2 files of 1 MB).

## Audit

Chatter keeps an audit log in the data volume: `logs/audit.log`, at most 2 files of 5 MB. For the lines and the format, see [Audit log](./guide/logs.md#audit-log).

- **Each change has a line.** After the login check, each request with a method that is not `GET` gets a line: the user, the role, the method, the route pattern, the IDs in the route, the status, and the address. The address comes from a trusted proxy, as for the login. A request that Chatter refuses (for example `403`) and a request that fails (`500`) also get a line. So a delete is in the audit log.
- **Each password try has a line.** Also each try with an unknown username: the server log drops these after 20 from one address in 15 minutes, but the audit log keeps all. The first-run setup, each refused setup, and `npm run reset-password` also get a line.
- **The audit log has no secret.** A line never has a value of the body or of the query, a password, a token, or a cookie. Chatter hides secrets in the details as in the server log.
- **Only an Admin can read a log.** The server log, the live log, the login log (**Settings > Logins**), the log of the update helper, and the support bundle (which has the audit log) answer `403` to a Viewer and to an Operator.
- **The audit log is not proof.** A person with access to the data volume or to the server can change or delete the file. When the card is too slow, Chatter can drop lines, and it writes how many. When the files are full, Chatter deletes the oldest lines, so many password tries can push old lines out. To keep the lines longer, copy the file to another computer.
- **A request with no login gets no `Change` line.** Chatter refuses it before it can change something. The login and the setup have their own lines.

## History backup of a machine

The **Advanced** panel of the Settings tab of a machine backs up its history to a file, and restores such a file (see [Back up and restore the history of a machine](./guide/get-started.md#back-up-and-restore-the-history-of-a-machine)).

- **The file has no secrets.** It has no machine settings: no address, port, user name, password, or macro. The manifest has only the id, the name, and the type of the machine. The alert rules are in it. A custom alert query can name other machines, so read the rules before you give the file to another person.
- **Only an Admin can restore.** A user with `manage-machines` can back up. Chatter logs each backup and restore with the user name.
- **Chatter checks all of a file before it writes anything.** It takes only the known entries, each with the size and sha256 of the manifest, and it never uses a name from the file as a path. A restore writes only `chatter_*` series with the labels `__name__`, `machine` and `type`, and changes only their `machine` label. It refuses a series with another label, or of another machine than the manifest names. So a file cannot change the history of another machine or the alert state of vmalert. Anyone who can edit the file can make the sha256 match again, so the check finds a broken file, not a changed one. An Admin must restore only files that they trust.
- **The limits protect the Pi.** A file is at most 2 GB, a line at most 1 MB, and a part at most 16 GB after unpacking. Chatter streams the upload and the download to the disk of the data volume (`history-backup/`), not into memory, and keeps 256 MB of the disk free. A backup can use only the free space of the disk. Only one backup or restore runs at a time. Chatter deletes these files at the end, after 30 minutes with no next step, when a request or a download stops, and at each start.
- **VictoriaMetrics exports block by block** (`reduce_mem_usage=1`), so the export of a long history does not fill the memory of the Pi.

## Keep `chatter.db` private

`chatter.db` is the database file. With Docker, it is in the volume `chatterbox-data`. It holds:

- The FTP passwords of the machines and the OPC UA passwords of Siemens machines, as plain text, because Chatter must send them to the machines.
- The Twilio auth tokens, the webhook secrets, the Discord webhook addresses, the Telegram bot tokens, the ntfy topics and access tokens, and the Apprise passwords of the notification channels, as plain text, because Chatter must send them to the service. Anyone with the file can send text messages with your Twilio account, can post to your Discord channel, can send messages with your Telegram bot, and can read and send to your ntfy topic.
- The usernames and roles. Each password is kept only as a hash (a one-way code, so nobody can read the password back from it).
- The logged-in browsers and the last 50 password tries, with their addresses. The audit log also has each password try. A login cookie is kept only as a hash, so the file cannot be used to log in.

The folder `opcua-pki` next to `chatter.db` holds the private key of the Chatter certificate for Siemens machines.

The file `device-key` next to `chatter.db` holds the key that signs the device cookies. Only the user that runs Chatter can read it. A person with this file and the password hash of a user can make a device cookie for that user. To stop all device cookies, delete the file and restart Chatter. Chatter then makes a new key, and each browser is new again.

Do not share these files. Keep their backups private, and also the backups of the machine history (the volume `victoriametrics-data`).

## Keep VictoriaMetrics and vmalert closed

VictoriaMetrics (the machine history database) and vmalert have no login. Anyone who reaches them can read and delete the machine history. Chatter's alert port 3002 has no login either: anyone who reaches it can add false alerts.

- `docker-compose.yml` does not publish these ports. Do not add a `ports:` line for `victoriametrics` or `vmalert`, or for port 3002 of `chatterbox`.
- VictoriaMetrics and vmalert are only on the Docker network `history`. This network is internal. So no other computer on the network can send packets to these containers, and these containers cannot connect to the shop network or to the internet. Chatter is on `history` and on the network `default`. Do not put `victoriametrics` or `vmalert` on `default`, and do not remove `internal: true`.
- Port 3002 of Chatter is on the network `default`. On Linux, a Docker Engine older than 28 lets a computer on the same network send packets directly to the address of a container. So that computer can reach port 3002. Use Docker Engine 28 or later (see [Install on a computer](./install/computer.md)). Each Pi card, from the first card of Chatter 1.0.0, has Docker 28 or later. The card build installs the newest Docker from the packages of Docker. An update of Chatter does not change Docker. To see the version, run `docker version` on the Pi.
- Each container on the network `history` can reach VictoriaMetrics and vmalert. Each container on the network `default` can reach port 3002. Do not add other services to this `docker-compose.yml`, and do not connect other containers to its networks.
- Without Docker, Chatter listens on port 3002 only on `127.0.0.1`. Change `ALERT_HOST` only to an address that other computers cannot reach.

Only an Admin can change the alert rules. A custom alert query can only read the machine history. It cannot change or delete data.

## Limit who can reach Chatter

On Linux, Docker sends the traffic of a published port around the rules of ufw and firewalld. So these rules do not limit port 3001. Use one of these two ways:

- **A rule in the `DOCKER-USER` chain.** Docker sends this traffic through that chain first. For example, this rule stops each computer that is not in `192.168.1.0/24`:
  ```bash
  sudo iptables -I DOCKER-USER -i <LAN interface> -p tcp -m conntrack --ctorigdstport 3001 --ctdir ORIGINAL ! -s 192.168.1.0/24 -j DROP
  ```
  Put your own network in place of `192.168.1.0/24`. To let only a reverse proxy through, put the address of the proxy there (see [Use HTTPS](./guide/https.md)). Put the name of the network interface of the computer in place of `<LAN interface>`, for example `eth0`. To see the names, run `ip -br addr`. With `-i`, the rule stops only the traffic that comes in from the network. So a proxy in a Docker container on the same computer can still reach Chatter. The rule is lost when the computer restarts. To keep it, save it, for example with the package `iptables-persistent`. This rule does not stop IPv6.
- **Publish the port on one address only.** In `docker-compose.yml`, change `"3001:3001"` to `"<address>:3001:3001"`, for example `"192.168.1.20:3001:3001"`, then run `docker compose up -d`. Chatter then answers only on that address of the computer, and not on IPv6. Each computer that can reach that address can still open Chatter. An update replaces `docker-compose.yml`, so do the change again after each update (see [Update Chatter](./guide/update.md)). On the Pi card, the update helper replaces the file, so use the `DOCKER-USER` rule.

## Locked out after wrong passwords

When Chatter says **Too many wrong passwords**, do one of these:

- **Use a browser that is already logged in.** A login lasts until it is not used for 14 days, and 1 year at most. The lock does not stop it.
- **Use a browser where you logged in before.** The lock does not stop a known browser. You can also change your password in that browser.
- **Ask an Admin to unlock you.** The Admin opens **Settings > Logins**, and clicks **Unlock** next to your computer or your username. When you are the only Admin, use a browser where you are already logged in. Chatter writes in the server log who unlocked and from which address.
- **Wait.** The lock ends 15 minutes after the first wrong password. **Settings > Logins** shows the time left.
- **Restart Chatter.** A restart ends each lock. Run `docker compose restart chatterbox` in the Chatter folder. On the Raspberry Pi card, first run `cd /opt/chatter`, and put `sudo` before `docker`.
- **Make a new Admin account.** This is the last step. Do it only when no Admin can log in. See [Forgot a password](#forgot-a-password). The command does not end a lock, so restart Chatter after it.

If the lock comes back again and again, someone on the network sends wrong passwords. Look in **Settings > Logins** and in the server log for the address.

## Forgot a password

An Admin sets a new one in **Settings > Users and roles**, with **Reset password**.

If no Admin knows their password, make a new Admin on the computer that runs Chatter. Run this in the Chatter folder:
```bash
docker compose exec chatterbox npm run reset-password
```
On the Raspberry Pi card, first run `cd /opt/chatter`, and put `sudo` before `docker`.

1. Type the username of the new Admin.
2. Type the password of the new Admin. Then type it again. The password does not show while you type it. It must have at least 8 characters.
3. Restart Chatter. Run `docker compose restart chatterbox` in the Chatter folder. On the Raspberry Pi card, put `sudo` before `docker`. The command cannot end the lock of a user, because Chatter keeps each lock in memory. A restart ends each lock.
4. Open Chatter, and log in with the new username and password.

If you do not restart Chatter and it says **Too many wrong passwords**, the username is locked. Restart Chatter, or run the command again with a different username.

The command asks for the password on the terminal. Do not give the password on the command line, because other users of the computer can see the command line. If the command says that it needs a terminal, do not use `docker compose exec -T`.

The command removes each Admin account and logs out every browser. After this, no browser is a known browser. The new Admin is a new account, also when it has the name of an old Admin. The Viewer and Operator accounts, your machines, and the upload history stay. Chatter does all of this in one step: if one part fails, nothing changes. The first-run setup stays closed, so no other person on the network can make the Admin.

If the username belongs to a Viewer or an Operator, the command shows a warning. To make that user the Admin with the new password, type `PROMOTE`. Any other answer stops the command, and nothing changes.

The command records the new Admin in three places. None has the password:

- **Settings > Logins** shows a row with the username, the address `server terminal` and the result **New Admin from reset-password**. The real Admin can see this row after the reset.
- The log file `logs/chatter.log` in the data folder gets a warning with the username. The [support bundle](./guide/diagnostics.md#support-bundle) has this file. The command writes the line only when the file exists, so it does not make a file that the server cannot write. The log view in **Settings > Diagnostics** does not show this line, because the command does not run in the server process.
- The audit log `logs/audit.log` gets a line with the username. The command writes it only when the file exists, as for the log file.

## Not in scope

- Problems in the machine controls, or in their own protocols
- Problems in the FANUC FOCAS2 library (report them to FANUC)
- Attacks that need access to the computer that runs Chatter, or to `chatter.db`
